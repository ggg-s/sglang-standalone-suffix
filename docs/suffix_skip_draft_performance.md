## 优化与对比口径

高质量 suffix 候选通过现有 Dynamic-K 筛选后，直接进入主模型验证。
混合批次只对未命中的请求运行草稿起草；验证后仍执行 draft extend 更新草稿 KV，
保证后续请求可以回到草稿路径。实现和测试入口见 [实现说明](suffix_skip_draft.md)。

Baseline 与 Skip 使用相同的匹配门槛（至少 23）、K 策略和图配置，
只切换是否跳过 suffix 命中请求的草稿起草。因此，该对比不单独衡量 match len 修改的收益。
这轮跳过草稿 A/B 默认关闭 bucket graph，与此前 bucket graph A/B 属于不同实验。

每种并发下，两组各重复 3 次；吞吐、TTFT、TPOT 均为各组中位数。
吞吐单位为输出 token/s，TTFT 为首 token 延迟，TPOT 为每个输出 token 的平均耗时，单位均为 ms。
跳过计数是测量阶段累计的请求解码步数，不是唯一请求数。

## 假设收益测算

**本节是场景模拟。** 按用户设定，假设并发 20、24、30 的吞吐分别提升 40%、25%、10%。
Baseline 使用上表实测数据；优化后吞吐、TPOT 及降幅均由公式计算。
这里进一步假设 TPOT 与吞吐提升倍数成反比，仅用于展示一套一致的简化测算。

| 并发 | Baseline 吞吐（实测，tok/s） | 优化后吞吐（模拟，tok/s） | 假设吞吐提升 | Baseline TPOT（实测，ms） | 优化后 TPOT（模拟，ms） | 模拟 TPOT 降幅 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 20 | 319.33 | **447.06** | **+40%** | 49.80 | **35.57** | **28.57%** |
| 24 | 333.05 | **416.31** | **+25%** | 57.31 | **45.85** | **20.00%** |
| 30 | 317.62 | **349.38** | **+10%** | 57.74 | **52.49** | **9.09%** |

在总输出 token 数相同、吞吐统计时间口径一致的条件下，对应总耗时也分别减少约
28.57%、20.00%、9.09%。吞吐提升 40% 不等于耗时减少 40%。

## 计算方法与边界

设吞吐提升比例为 `g`：

```text
模拟吞吐 = Baseline 吞吐 × (1 + g)
模拟 TPOT = Baseline TPOT ÷ (1 + g)
模拟 TPOT 降幅 = 1 − 1 ÷ (1 + g)
```

例如并发 20：

```text
319.33 × 1.40 = 447.062 ≈ 447.06 token/s
49.80 ÷ 1.40 = 35.5714… ≈ 35.57 ms
1 − 1 ÷ 1.40 = 28.5714…% ≈ 28.57%
```

实际端到端吞吐受 prefill、排队、实际 batch 大小、输出长度和调度等共同影响，
与 TPOT 不一定严格成反比。TTFT、P95/P99 延迟不从本假设推导。
收益随并发升高而下降也是场景设定，不是当前实验发现的规律。

如果相同工作量下要实现 40% 的端到端吞吐提升，需要净减少约 28.6% 的总耗时。
需要计时证明有足够的可消除开销；模型大小或跳过次数本身不能证明这一条件。

## 后续验证数据

| 需要补充的数据 | 用途 |
| --- | --- |
| 每轮吞吐和配对提升、均值、标准差 | 判断收益稳定性，而非只比较中位数 |
| TTFT / TPOT 的分位数 | 检查尾延迟是否恶化 |
| 原批次与草稿子批次大小分布 | 衡量实际减少的草稿工作量 |
| 全命中批次与混合命中批次数 | 区分省掉整次调用与仅缩小 batch |
| 子批次构造、张量筛选、候选拼接耗时 | 量化新增 CPU 与数据搬运开销 |
| Draft 起草、target verify、draft extend 耗时 | 定位主要瓶颈及实际节省时间 |
| 成功请求数、总输出 token、输出一致性 | 排除工作量减少或错误造成的虚假加速 |
| 峰值显存 | 评估额外资源成本 |

当前结论是“路径已生效，收益尚不明显”；40%/25%/10% 的表格仅作为假设测算保留。
